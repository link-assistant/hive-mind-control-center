**Confirmed root cause: repository-scoped Codex authentication copies diverge after refresh-token rotation.** The surviving task has refreshed credentials in its own scope, while the bot and new tasks continue reading the stale source credentials. This explains why one Codex task can keep working while `/limits` and a newly launched task fail authentication.

I investigated with the control-center auto-fix script's diagnostic and read-only collection modes, then compared existing execution logs, credential state, process configuration, container mounts, and the deployed implementation. The detailed evidence is retained locally. No credentials were changed and no tasks were restarted during the investigation.

**Observed behavior**

| Consumer | Result of the comparison |
| --- | --- |
| Bot `/limits` | Still reads the original credential generation; existing request logs transition from successful usage responses to an expired-token response. |
| Surviving Codex task | Runs with a repository-scoped `CODEX_HOME` and has a refreshed credential generation there. Its execution continues producing new tool calls after the bot's auth failures. |
| Failed task for this issue | Its newly created scoped credential file contains the same stale credential generation as the bot's source. Refresh is rejected because the refresh token was already used. |

The shared base credential file is present and accessible to both the bot and the surviving task. The important difference is the additional scoped copy that Codex actually uses. A recently copied file also has a recent filesystem modification time even when the credentials inside it are stale.

The failed Codex attempt is already documented in [PR #3786's failure report and linked log](https://github.com/link-assistant/hive-mind/pull/3786#issuecomment-6399359207). The explicit error is that the refresh token was already used. The surviving task's continued activity is supported by new execution output, beyond the queue's `processing: 1` counter.

The sequence established by these observations is: a task starts from the shared credentials; Codex refreshes its scoped copy; the shared source remains unchanged; its access token expires; `/limits` fails; a new task copies that stale source and cannot reuse its already-consumed refresh token. The historic token-exchange response was not captured, so identifying the surviving task's refresh as the consumption event is an inference from the credential comparison, code path, and explicit reuse error together.

**Implementation defect**

The published implementation shows the full mechanism:

- [`syncFileIfPresent()` unconditionally uses `fs.copyFile(source, target)`](https://github.com/link-assistant/hive-mind/blob/6efc9b441d4c18ae27d85cf4280352b9582a6078/src/codex-capability-preflight.lib.mjs#L564).
- [`prepareScopedCodexHome()` copies the base authentication file into a repository scope](https://github.com/link-assistant/hive-mind/blob/6efc9b441d4c18ae27d85cf4280352b9582a6078/src/codex-capability-preflight.lib.mjs#L711), and [scoped operations receive that home through `CODEX_HOME`](https://github.com/link-assistant/hive-mind/blob/6efc9b441d4c18ae27d85cf4280352b9582a6078/src/codex-capability-preflight.lib.mjs#L878). Refresh writes update this private copy without reconciling the base credentials.
- [The isolation mount contract](https://github.com/link-assistant/hive-mind/blob/6efc9b441d4c18ae27d85cf4280352b9582a6078/src/isolation-runner.lib.mjs#L119) promises credential sharing, but mounting the base file does not make a separate scoped copy share subsequent updates. The updated copy can also disappear when the task's writable layer is cleaned up.
- [`getCodexUsageLimits()` reads the base credentials and maps an HTTP 401 usage response to the displayed authentication-expired error](https://github.com/link-assistant/hive-mind/blob/6efc9b441d4c18ae27d85cf4280352b9582a6078/src/limits.lib.mjs#L803). It does not coordinate credential refresh.
- [Subscription dates are decoded separately from stored JWT claims](https://github.com/link-assistant/hive-mind/blob/6efc9b441d4c18ae27d85cf4280352b9582a6078/src/limits-subscription.lib.mjs#L172). A displayed future subscription date can coexist with expired request credentials; that date is stored metadata rather than a fresh entitlement check.

[Official OpenAI documentation](https://learn.chatgpt.com/docs/auth#credential-storage) confirms that file credentials are stored under `CODEX_HOME` and that Codex refreshes ChatGPT tokens during use. The scope selected for those writes therefore matters.

**Reproduction and prevention**

An offline reproduction passed using the deployed copy function with synthetic credentials: copy an initial credential into task A; simulate rotation by replacing A's scoped credential; create task B through the same function. A retains the replacement, while the base and B retain the consumed predecessor. Running preflight again for A also overwrites its refreshed credentials with the stale base copy. This verifies two storage defects without using real credentials or making provider requests.

**Required default behavior: the host system, root/bot container, and every task container MUST use the same host-backed authentication and conversation-history storage for each tool.** This applies to Claude, Codex, and every other supported tool unless an explicit opt-out selects an alternative isolation/authentication system as described below. In the default mode, the same account must never acquire a second mutable auth file in a repository scope, container layer, image, recovery snapshot, or temporary home. Periodic synchronization and copy-on-start/copy-on-exit do not satisfy this requirement.

**Sharing must be enabled by default, with an explicit opt-out configuration available.** Fresh installs, upgrades, normal task launches, repository-scoped tool homes, and restart/resume/recovery must establish and enforce shared auth and conversation storage automatically, without an enabling flag, environment switch, manual symlink, or post-task synchronization step. Ordinary path/configuration overrides must not accidentally disable sharing. If default-mode canonical storage cannot be established, reject the launch rather than silently opting out or falling back to private copies.

**Explicit alternative mode:** allow a documented opt-out to delegate isolation and credential handling to another selected system, such as [Link.Assistant.Router](https://github.com/link-assistant/router). Router is still experimental and under development; this is a compatibility requirement, not a claim that its integration is already complete. Its [documented design](https://github.com/link-assistant/router/blob/main/README.md) keeps vendor credentials inside Router and gives tasks their own revocable tokens. In that mode, do not force vendor credential mounts into task containers or mistake intentionally distinct Router task tokens for divergent copies of vendor refresh credentials. Make the selected authority/mode explicit in configuration and diagnostics, validate its storage and conversation-audit contract, and test it separately. Conversation evidence must still be durably collected for debugging and security audit through the selected backend. Backend failures must not silently switch modes or expose a local vendor-auth fallback. The mount-specific requirements below apply to default mode; an explicitly selected alternative must enforce its own declared authority and persistence contract.

In default mode, define one explicit shared-state manifest per tool and enforce it across the full storage chain:

`host canonical storage → root/bot container mounts → task container mounts → tool's effective scoped paths`

- **Authentication:** mount the host's canonical credentials into the root container and expose the same backing storage to task containers. Every effective tool home, including repository-scoped homes and environment/CLI overrides, must resolve authentication to that storage. Refresh, reauthentication, and logout must update the canonical state; a task must never silently fall back to a private credential copy. Serialize refresh across processes and containers, with a re-read of the canonical generation before exchanging a refresh token, so concurrent participants cannot reuse a consumed predecessor.
- **Conversation evidence:** persist sessions, projects, transcripts/rollouts, archived conversations, and the indexes or metadata needed to discover, resume, and audit them in the host-backed shared state. Writes from any task must be available from the host, root container, and other authorized tasks. Task completion, container removal, restart/resume, deployment, and image cleanup must preserve this evidence. This is required both for bug diagnosis and security audit; a transcript copied out only after successful completion is insufficient.
- **Configuration isolation:** configuration, skills, plugins, and other task-specific settings may differ. Keep their isolation while preventing any setting, scoped home, or preflight step from redirecting auth or required conversation storage to an independent copy. Classify shared conversation metadata explicitly rather than assuming every state database is task-local.
- **Mount/write semantics:** verify actual backing mounts and the paths the running tool uses. Resolve mount sources in the Docker daemon's filesystem namespace, including host-socket and nested-daemon launch paths. Sharing must survive the CLI's actual write behavior, including temporary-file-plus-rename replacement, deletion/recreation, and reauthentication. Equal initial contents, matching pathname strings, or the existence of a bind mount/symlink alone do not prove this invariant. Every participant's next credential read must see the same committed canonical generation.
- **Runtime enforcement:** validate the invariant before any authenticated task starts, after scope/preflight preparation, and on resume/recovery. Missing mounts, an unexpected source, a private auth/history copy, or a scope that cannot share required history must stop the launch with an actionable error. A warning followed by continued execution is not acceptable. Detect and stop use of divergent storage if a running process changes its effective paths.

**CI/CD must enforce this as a required release and deployment gate.** Add real Docker integration tests using disposable host directories, synthetic credentials, and a local provider stub where refresh needs to be simulated. Run the production mount-building and scoped-home code, exercise the supported CLI versions' storage behavior, and make tool upgrades pass the same checks. Unit tests or equal-content assertions alone are insufficient.

| Required CI/CD check | Required assertion |
| --- | --- |
| Default execution with no opt-out, no sharing flags, and no special setup; fresh and upgraded deployments | Sharing is active automatically for every supported tool and launch path. Ordinary overrides cannot silently select private auth/history; missing mounts do not implicitly enable opt-out. |
| Explicit opt-out selecting Router or another alternative isolation/authentication backend | Validate the selected authority and durable conversation-audit contract. Router mode does not mount upstream vendor credentials into task containers. Test mode selection, per-task token isolation, restart/resume, failure handling, and absence of silent fallback to default/local vendor auth. |
| Every supported tool; root plus two concurrent task containers, including different repositories | Each effective auth and conversation path resolves to the approved host backing store. A copied credential file with identical contents must fail validation. |
| Updates initiated from the host, root container, and either task | Refresh/reauth/logout changes are observed on the next read by every participant; no stale private generation survives. Cover in-place writes and atomic replacement, not only initial mount creation. |
| Concurrent refresh and repeated capability preflight | Refresh is coordinated; no consumed-token reuse, lost update, or overwrite of current canonical credentials by an older copy. |
| Session/project/rollout and history-index writes from each task | Host, root container, and another authorized task can discover the same persisted conversation; a fresh container can resume it where the tool supports resume. |
| Task success, failure, forced termination, removal, restart/resume, deployment, and cleanup | Canonical auth and audit conversations remain intact and usable. Recovery snapshots cannot restore a private stale auth file over canonical storage. |
| Deliberately missing/wrong mounts, broken links, private fallback files, and overridden tool homes | Production startup validation rejects the task before tool execution. Confirm configuration can still differ while auth/history cannot diverge. |
| Supported host-Docker and nested-Docker paths and release images | Validate the actual filesystem behind each mount rather than assuming a path inside the root container is a valid host-daemon source. The packaged/deployed image must pass, not only a development checkout. |

The default-mode suite and coverage of explicit alternative-mode selection must be required by the release/deployment workflows; a skipped Docker suite, unsupported storage contract, or failed invariant check must block promotion. Deployment preflight must validate the real configured mounts in default mode or the selected backend contract in explicit alternative mode before admitting tasks. Keep test artifacts limited to synthetic values and structural results; credentials and conversation contents must not be published in CI logs.

`/limits` must use the selected authentication authority: the canonical, coordinated shared state by default, or the explicitly configured alternative backend. It must distinguish stored subscription metadata from a current authenticated request. The scope-copy root cause above should be considered fixed only when these shared-storage and lifecycle tests pass. These are required acceptance criteria for the implementation, not a claim that the checks are already implemented or passing.

Before recovery or cleanup, preserve the surviving task's refreshed credential state through a secure recovery procedure. Reauthentication can restore access, but the copy/rotation defect also needs fixing to prevent recurrence. This investigation did not perform that recovery. Claude subscription detection and the separate display-layout changes remain implementation work for this issue.
